# 数据集构造与使用协议

## 数据集的三种角色

本项目必须严格区分同一案件的三种数据视图。

1. 原始档案视图：保存法院事实、裁判说理和裁判结果等全部可用字段。
2. 参考标签构造视图：允许使用原告诉请、裁判说理和裁判结果生成`claim_results`与`payment_result`。
3. 结果盲实验视图：必须排除裁判说理、裁判结果及其任何派生信息。

当前5,134条LexChain数据属于第二种视图，只能作为参考标签候选，不能直接作为MAIN-1的模型输入。

## 当前语料规模

- 统一后的原始记录：5,712条。
- API处理前排除：578条。
- 符合条件并完成处理：5,134条。
- Qwen Batch成功：5,134/5,134。
- JSON及本地摄取错误：0。
- 确定性QC候选集：3,161条。
- 人工复核集：1,973条。

排除规则要求案件具有可用的法院事实和裁判结果。正式论文必须继续报告具体排除原因。缺失文书字段的案件可能在来源、年份、复杂度或公开质量方面与保留案件不同，因此不能把5,134条描述为未经筛选的中国侵权案件样本。

## 请求级参考结构

每条记录保留`lexchain-reference-v1`外层结构：

- `schema_version`
- `queue_index`
- `case_id`
- `train_input`
- `gold_output.claim_results`
- `gold_output.payment_result`
- `quality_control`

`quality_control.passed=true`只表示记录通过了当前确定性一致性与原文定位检查，不表示已经经过人工完整性和法律正确性验证。

## 数据发布层级

必须明确区分以下层级：

- `human_gold`：经过独立人工复核及分歧裁决。
- `qc_candidate`：通过确定性QC，但尚未完成人工复核。
- `review_required`：触发一个或多个确定性QC问题。
- `source_excluded`：缺少参考标签构造所需的源信息。

论文主测试应以`human_gold`作为参考答案。较大的`qc_candidate`集合只能用于明确标注的敏感性分析或后续训练实验。

## 信息泄漏控制

### 法院查明事实

`court_found_facts`虽然通常不直接包含裁判主文，但它不是中性的原始证据，而是法院完成证据选择和事实认定后的结果，可能隐含裁判路径。MAIN-1必须明确其目标是基于法院已认定事实生成说理，或者进一步从当事人陈述和证据摘要构造更严格的输入。SUP-4应专门测量这一输入边界的影响。

### 候选法条

如果`law_candidates`依据测试案件原判引用的法条生成，就会泄漏法院的规范选择。正式主实验前必须记录每个候选列表的来源；凡使用原判说理或法条引用生成的候选集合，都应改用不读取测试裁判的检索方法重新生成。

### 数据切分与重复案件

必须按案件组切分，不能仅按数据行随机切分。下列记录应放在同一组：

- 完全重复或近重复文书；
- 同一案件的不同版本；
- 一审、二审或再审等关联程序；
- 来自同一基础纠纷的多份裁判。

冻结测试集时，还应检查法院、年份、来源和案件类型分布。

### 提示词开发

所有提示词和QC调整只能依据开发集进行。第一次正式测试前，必须同时冻结测试集、提示词、输出结构、模型快照、解码参数和统计方案。

## 参考标签构造规则

- 诉请项目只能来自原告诉请原文。
- 裁判说理和主文只能决定结果、支持金额、裁判操作和付款关系。
- 诉请仅列多个项目但只有一个总额时，保留一个复合金额诉请。
- 多个独立诉请共享无法分配的合并判赔时，不平均分配，不按比例猜测。
- 诉讼费、迟延履行提示及被告内部追偿不进入实体付款结果。
- 非金额救济的行为、对象、平台、范围、公开方式或期限发生缩减时，应标为部分支持。

## 人工复核优先级

优先处理以下高风险记录：

- 两个以上付款义务；
- 保险、连带、按份或补充责任；
- 无法分配的合并判赔；
- 五项以上金额诉请；
- 多项非金额救济；
- 撤回或未处理诉请；
- 付款总额与诉请支持额不一致；
- 原文定位失败。

对QC通过记录也必须按诉请数量、付款义务数量、案件类型、数据来源和裁判结果分层抽样，报告人工准确率及置信区间。

## 隐私与公开发布

不能因为处理代码已经公开，就自动公开案件全文。优先发布代码、提示词、数据结构、汇总统计、文件摘要和合成示例。只有在确认数据许可、个人信息保护、匿名化和机构审批条件后，才能发布案件原文或完整模型输出。
